# Terrain cache recovery

Previously loaded terrain must not be treated as a cache hit after its backing canvas loses its context. Context loss invalidates raster readiness; restoration invalidates it again and reacquires the 2D context. Until restoration, render the same base terrain directly with the existing water-layer options. Do not mark a lost context ready during background warming. Released pages must also become unrendered.

Before preparing any visible page, protect every page in the current viewport from eviction, including pages later in draw order. Keep byte budgets and normal offscreen LRU eviction.

## Hot-path audit

`renderTiles` runs once per rendered frame, independent of entity count. The added viewport pin pass performs one key/Set insertion per visible chunk, replacing insertions in the draw pass and reusing the existing Set. Context availability adds one optional native query per visible chunk and per cache update; event closures are allocated only when creating a page. No added raster overdraw on healthy frames and no change to DPR, source imagery, resolution, water animation, or visual detail. Direct fallback uses the existing tile path only while a cached context is unavailable.

## Staging contention recovery (2026-10-28)

Incremental decoration work can retain the single-page `terrainStaging` reservation between animation frames. Foreground terrain must preempt that unpublished work before reserving staging; it must not throw, display an empty page, or keep drawing every cold page directly because staging is permanently occupied. Cancelled work releases its staging token and backing canvas. The last published decoration canvas and its resident reservation remain valid throughout replacement preparation. Only a complete replacement moves from staging to resident ownership; capacity failure leaves the last published page intact. Resident admission failure uses the existing full-quality direct terrain path without increasing byte limits. Background cache trimming protects the current viewport.

Reproduction: on current dev before this fix, start `processDecorativeWarmQueue` with a deadline permitting one tile, then call `renderTiles` with another cold chunk visible. `terrainStaging byte budget exceeded` escapes after the game canvas clear; `GameLoop.animate` does not reach its next scheduling call. U07037 reproduces this with ordinary default budgets; U07041 checks published/staged ownership and cancelled backing-store release. U07038–U07040 cover bounded resident pressure, viewport preservation, and released readiness. E00244 uses real browser 2D canvases, partial decoration preparation, camera jumps/reversals, and opaque terrain samples. It is a functional correctness test, not a GPU/performance benchmark.

Hot-path audit: admission/preemption runs on raster cache misses, once per chunk preparation rather than per entity or pixel. It scans at most the bounded 12-entry decoration queue only if staging is occupied. Cache-hit frames retain their existing draw path; published decoration detail, DPR, resolution, and animation settings are unchanged. No staging/resident budget is enlarged. Hardware 75 FPS acceptance remains pending under the protocol above.
