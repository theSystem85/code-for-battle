# GPU-parallel impact particle assessment

The candidate was to evaluate impact positions, ages and fades per instance in a GPU vertex shader. The existing impact pool is bounded to 384 particles on desktop and 128 on the low-quality path. At 60 FPS that caps the position and lifetime work at 23,040 desktop particle visits per second. At DPR 2 a CSS-pixel coverage area maps to four backing pixels. Higher DPR increases raster work and leaves the number of particle instances unchanged.

An instanced path could replace some Canvas 2D submissions. It would need to preserve fog visibility, blended orange band opacity, the additive core and sparks, smoke and scorch order, continuous scale and lifetimes. An additional WebGPU surface would also introduce another compositor layer in the exact path that stalled in the hardware trace. A separate compute dispatch would have a further cost. Use the same render target and instanced geometry first if future GPU captures show that this work is material.

The production benchmark records existing per-frame render phases. The effects phase measures CPU submission for all effects, including fire, projectiles, smoke and explosions. It is an upper bound on CPU submission for impact particles and does not isolate their GPU raster cost. The earlier [Chrome GPU process trace](2026-11-18-chrome-presentation-trace.md) attributes the dominant observed delay to buffer swaps and presentation waits. It cannot assign GPU raster time to individual game effects.

The stationary capture and reproduction command are in the [production hardware report](2026-11-18-physical-display-acceptance.md). The particle implementation remains conditional on evidence from a physical-display capture. There is no before/after FPS gain to report for a particle shader.

In the 60-second production run after the worker fix, the game reached 18 Apache rockets and 18 impacts whose centers were in the viewport. The overall effects phase averaged **0.26 ms**, with **0.70 ms p95** and **0.80 ms max**. CPU simulation averaged 41.46 ms, and callbacks averaged 2.097 FPS with a one-second minimum of 2 FPS. Even eliminating all of the measured effects submission would recover less than 1 ms per measured frame. The evidence does not justify replacing the impact renderer with a GPU particle pipeline before the presentation stalls are characterized on a physical display.

The [active-display follow-up](2026-11-18-active-display-fps.md) confirmed the 0.70 ms effects CPU p95 and measured up to 954.97 ms of Core Animation backpressure in a swap. Chrome did not attribute individual raster commands to particle effects. The condition for a GPU particle implementation remains unmet.

The [impact draw attribution experiment](2026-11-18-impact-draw-attribution.md) bypassed all pooled impact drawing in two of four hardware captures. It measured a 0.45 ms reduction in CPU effects submission p95 with essentially unchanged presented FPS. This completes the conditional assessment.
