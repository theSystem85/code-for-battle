# Dense battle performance: next implementation checklist

Start with items 1 and 2. The highest-value question is which game surface or scheduling condition triggers the near-one-second presentation gaps. A smaller CPU frame still matters because simulation alone can exceed the 16.67 ms budget. The primary acceptance scene is a **stationary camera over the loaded Apache battle**. Scrolling is a separate regression check.

## Prioritized work

1. [ ] **Make the stationary comparison repeatable and fail clearly on an invalid run.** Extend `scripts/benchmark-unit-heavy.mjs` with a compact run manifest and paired runner. Record the actual served bundle hashes, fixture SHA-256, browser, physical display mode, adapter, active backend, CSS and backing dimensions, focus and profile flags. The local 5,655,791-byte reference save has SHA-256 `65acf030a1655055d1ed954fbdf9038919eb88e69e59b877f8427f33cdc7e1ce`. Provide a portable fixture or versioned generator with a verified scenario fingerprint. Today's generated save lives under ignored `tmp/`. Today the harness checks Apache activity only when the impact probe is enabled, records page errors, and accepts any starting army of at least 400. Check tutorial absence from startup, defeat and pause throughout capture, actual camera coordinates at render, visible unit counts, volley and impact activity in multiple windows, and simulation ticks advanced. Record expected ranges from repeated controls. Add a host-side timeout that still writes partial diagnostics if callbacks cease. **Done when** two fresh checkouts can reproduce a comparable pair, and deliberately wrong fixtures, backgrounding, empty combat and a stalled callback each yield a specific invalid-run result.

2. [ ] **Locate the missing frames between scheduling, rendering and presentation.** Extend the presentation reporter to emit a per-gap timeline. Match game scheduling source/delay, callback start, fixed ticks, render submission, compositor BeginFrame, swap, backpressure and presentation. Reuse the scheduler fields in `src/game/gameLoop.js` and existing phase counters. Tag the first on-screen rocket, impact and sprite explosion. Use trace flow or frame identifiers where available and label unmatched events. Select the ten longest gaps and adjacent healthy frames. Run a small continuously animated canvas on the same display through the same headed harness as a positive control. Compare minimal presentation tracing against tracing plus CPU profiling to quantify observer cost. **Done when** another agent can identify the first delayed stage, or see exactly where tracing loses the frame. Test parsing offline with duplicate feedback, multiple renderer PIDs, capture-edge gaps, missing marks and a zero-frame window. Distinguish missing telemetry from zero confirmed presentations.

3. [ ] **Isolate the contributing canvas or layer, then fix the measured cause.** Start at `src/rendering/renderer.js` (`renderGame`) and `src/game/gameLoop.js` (`renderMinimapIfDue`). The game clears a 1900 × 1478 backing surface and draws a transparent foreground above GPU terrain. Full coverage is 2.81 million backing pixels per frame before blending; actual raster damage needs measurement. In private benchmark modes hold one layer's last image at a time: GPU terrain, main 2D foreground, then minimap. Keep the rest of the scene animating, the layer participating in composition, and simulation running. Count actual draws/submits and compare damage bounds, swap waits and presented FPS. Split a positive foreground result into entities and selection overlays, sprite-sheet explosions/fire, and HUD. If holding layers individually has little effect, compare the same moving content on one versus stacked surfaces in a small reproduction and repeat on a second hardware browser or Chrome build. **Done when** a reversible toggle removes and restores the stall in paired runs, or the report narrows the failing combination. Candidate fixes include eliminating a proven redundant surface write or retaining valid pixels outside damage bounds. Verify transparent overlaps, old and new sprite bounds, terrain animation and device-loss recovery at full DPR before shipping.

4. [ ] **Measure CPU per simulation tick and reduce dense neighborhood work.** The fixed-step loop can run several updates after a delayed callback and caps foreground delta at 100 ms. Add ticks per render, simulated milliseconds per wall second, and per-tick p50/p95/p99. Use a fixed-tick replay of the same save for CPU comparisons. Instrument `src/game/spatialQuadtree.js` and callers in `src/game/movementCollision.js` for rebuilds, visited nodes, candidates and accepted neighbors by domain. Compare the hottest caller against the existing movement collision index before changing either structure. Reuse per-tick data only while positions and query semantics remain valid. **Done when** matched ticks take less CPU, state digests and ordered collision outcomes agree, and the live benchmark reports simulation throughput alongside min/avg presented FPS. Cover center-based tiles, self-exclusion, moving neighbors and air/ground separation.

5. [ ] **Measure first-use terrain and sprite preparation during cold traversal.** The first traversal and subsequent laps saw different combat populations. Create a matched route replay with the same world state at traversal start and explicit cold versus prepared cache state. Keep animated water and selected layered units active. Join page misses, atlas requests, upload bytes, worker completion, evictions and memory high-water marks to long frames. Inspect `src/rendering/prepared/` and `src/rendering/spriteStreamingDiagnostics.js`. If a repeatable miss leads a stall, prepare the specific page or final-size sprite within the existing byte budget. **Done when** first-traversal tails improve on matched content, with load-to-ready time, peak bytes and steady-state FPS reported. Recheck the stationary scene separately.

6. [ ] **Trial parallel work only for a measured critical path.** If item 4 finds a dominant read-only spatial/AI job, prototype a worker using packed reusable buffers and tick IDs. Measure snapshot creation, queue wait, compute, return and main-thread consumption. Preserve deterministic ordering and reject stale results. If item 3 finds a dominant GPU draw group, prototype batched instances on that group, measuring upload, GPU pass and presentation independently. Keep the prototype whose end-to-end gain survives transfer and synchronization. **Done when** the full-quality path beats control beyond run variation on the hardware battle, maintains state or pixel parity, and exercises its fallback. Close this item with the evidence if neither prerequisite is met.

## Reporting and acceptance

Use the [production setup](2026-11-18-physical-display-acceptance.md) and [before/after commands](2026-11-18-combined-cpu-gpu-fps.md). Run comparisons serially on verified hardware with an active display, a fresh headed browser, file import, `?tutorial=0`, defeat protection, the same save and the same fixed camera. Use separate directories. Keep the original full 60-second window and show the first ten seconds separately so a cold stall remains visible. Diagnostic layer bypasses measure attribution; final acceptance runs exercise the full game.

For each fix, commit its report under `docs/performance/`. Record A1/B1/B2/A2 results individually, absolute and percentage change in **average presented FPS**, **minimum presented frames in a rolling second**, frame p95/p99/max, intervals over 16.67 ms, simulated ticks/s, CPU update per tick, render submission, and GPU timings where available. Include build and fixture fingerprints and a link or reproduction command for the artifacts. Use same-build A/A repeats to estimate noise and repeat ambiguous pairs. Keep “valid run”, “demonstrated improvement” and “met the 60 FPS gate” as separate outcomes. A gain at one workload establishes a result for that workload; record verified unit counts and camera conditions.
