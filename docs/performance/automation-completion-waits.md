# Completion-wait runtime diagnostics

Run `node scripts/benchmark-automation-completion-waits.js`. Raw five-pass output is in [automation-completion-waits-cpu.json](automation-completion-waits-cpu.json). This diagnostic uses 800 pending unit waits (200 units, four bindings), a synthetic stress load of 160 pending production waits, 150 ms control cadence and 1,000 ms production cadence. The 160 production records exceed the representative 20-program scene and are deliberately classified as stress. Each pass covers 200 control batches and 4,800 production evaluations.

Exact unit target lookup rebuilds reusable unit/building indexes once per control batch, with 200 rebuilds and 40,200 indexed entities per pass. Pending completion results share an immutable status object; receipt/objective payloads allocate on accepted commands or actual status changes, rather than cloning every poll. Production receipts advance through item completion/cancellation events and exact authoritative acknowledgements, with at most one active receipt per saved program revision, a maximum 20-item stack and bounded duplicate-item identities. Finished, disabled, revised or removed programs release receipts; restart resets providers and unit target watches. Snapshot ACK fallback checks a receipt exists before constructing an acknowledgement.

Raw batch p95 values were 0.221–0.378 ms in the first four passes; a warm batch maximum reached 3.177 ms, and the cold first pass maximum was 1.621 ms. These are Node CPU diagnostics, not a full-game frame-time pass or a guarantee about allocations. Heap deltas include GC and are not precise allocation measurements. See the raw file for all five passes, p99/max and heap deltas.

The repository’s 75 FPS / 13.333 ms presented-frame gate remains open on qualifying hardware. This environment cannot certify rendering/GPU/scrolling performance. The orchestrator runs the integrated full suite, real production browser regression and whole-game headless diagnostic after integration.
