# Automation runtime CPU diagnostics

Reproduce with `node scripts/benchmark-automation-runtime.js`. Raw output is in `automation-runtime-cpu.json`. The fixture executes seven-state IF cycles, five reference/compiled pairs of 100,000 evaluations, and 200 cadence batches of 960 bindings (200 units and 40 defences, four bindings each). Sensing is deliberately absent; this measures machine overhead, not combat query cost. No compiler/parser runs in these evaluation batches. Cadence remains 150 ms for control and 1,000 ms for production.

Before hot-path edits, the main reference implementation measured five 100,000-evaluation passes at 31.003, 36.361, 40.902, 34.852 and 35.516 ms on Node v24.19.0. Later concurrent suites and browser benchmarks heavily contended the shared host. Current raw results therefore cannot be compared against that initial baseline as a valid performance improvement/regression claim. Reference/compiled pairs in the same run are diagnostic only; there is no unconditional speedup claim.

CPU machine work is independent of canvas DPR. The maximum representative control workload is about 6,400 evaluations per second, plus 18,000 early-out checks per second at 75 simulation updates. The compiled artifact resolves state/rule identities and prepares condition instructions and enemy dependencies outside gameplay. Runtime still allocates bounded outcome/history records, preserving reference semantics; compiler preparation does not eliminate those allocations or spatial sensing costs.

Qualifying hardware remains required for whole-game cold traversal, repeated scrolling, selected layered entities, movement/firing/water, FPS, p95/p99/max and missed 13.333 ms deadlines, GPU/backend/DPR and memory/GC evidence. Node/headless/software results cannot certify 75 presented FPS. The engineering active-batch 1 ms budget is not certified on this shared host. Root orchestration owns the full-game baseline/after diagnostics and retains the hardware gate as open.

After engine integration, `automation-runtime-cpu-after.json` records five comparable reference/compiled pairs in one Node process, including the cold first pair. Reference passes were 37.561–46.142 ms and compiled passes 42.275–49.674 ms per 100,000 evaluations. The cold compiled pair was slower; warmed pairs were close. This fixture establishes no general speedup. A 960-binding active cadence batch measured p95 0.713 ms, p99 0.976 ms and max 1.121 ms; this remains a CPU-only diagnostic with no sensing/render/GPU certification. The separately captured pre-edit baseline is not a controlled before/after game benchmark and cannot certify no regression.

The engine consumes prepared artifacts from accepted save/load revisions. Leaf parameter defaults, comparison modes/tolerance/circular comparisons, state/rule lookup and enemy dependency mask are prepared off-loop. The existing shared sensing scope and reusable 250 ms count/service indexes are retained; negative nearest-enemy results now survive command checks and repeated effects within the current entity evaluation. A new entity/evaluation resets sensing. Equal-distance selection uses stable ID ordering. Production remains at its 1,000 ms cadence; snapshot providers preserve pending simulation-time AFTER deadlines across save/load and ignore non-authoritative host copies of local production progress.

Replay records accepted unit command outputs after the adapter succeeds, with resolved target references, rather than evaluating CFBL again. Source-edit records restore source and binding intent; bounded runtime-change records restore state/hold/delay/completion for inspection. Idle and held reassertions do not snapshot every evaluation. Production uses its existing queue/spawn replay output path and its live engine is disabled during replay. Defence command intent outputs are supplied by the defence adapter package through the same output-only replay principle.

`node scripts/benchmark-automation-compile-stress.js` measures a seven-state machine expanded to at least 64 KiB of JSON. Raw results in `automation-compile-stress.json` measured compilation p95 6.612 ms and max 8.728 ms over 50 samples. This is explicitly a JSON machine stress diagnostic, not the exact 64 KiB CFBL-source fixture or a hardware release certificate.
