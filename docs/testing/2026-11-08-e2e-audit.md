## Q05 — Are E2E tests disabled on Netlify?

They are **not invoked** by `netlify.toml`. Its command runs `npm ci --include=dev && npm run build && npm run test:smoke`. The smoke command is one Vitest/jsdom integration test, not Playwright Chromium. A Lighthouse build plugin also runs; that is separate from the Playwright suite and from the game’s hardware FPS acceptance. GitHub Actions only triggers for main and runs lint, unit/integration, build, and the same smoke command; it does not run Playwright. No dev Actions job or E2E schedule exists.

## Q06 — Are E2E tests disabled in coding-agent cloud VMs?

At least 57 test files directly import `/src/` modules; many are browser integration/scenario tests rather than purely external UI tests. Those cases require Vite source serving and cannot run unchanged against a compiled Netlify deployment.

No generic cloud-VM guard exists in Playwright configuration. CI changes retry/worker settings; it does not disable execution. AGENTS.md requires E2E before code pushes, but that is agent policy rather than an automatic hook. Docs-only changes skip tests unless the user explicitly requests testing, as here. Browser binaries, Linux browser dependencies, a reachable local server, and any required network/backend access must be prepared in the VM. Some tests opt into performance through environment flags, iOS tests require separate device/simulator setup, and some GPU tests self-skip on missing hardware. These checks are inconsistent across files: a software VM must not run GPU/performance acceptance tests under the repository rules.

## Q07 — What is the most efficient place and schedule?

Recommendation (not implemented):

- During coding: run the relevant behavior tests against localhost. Use stable test IDs to target failures.
- Before each code push to dev: retain the existing required lint/unit/integration/E2E policy until Patrick explicitly changes it. The policy is before every push, not necessarily every intermediate local commit.
- After a healthy baseline exists: consider a small critical smoke/regression set before every push, plus full functional tests nightly and before releases. This would require updating the existing validation policy; a nightly run alone detects regressions after they have already reached dev.
- Nightly: use a dedicated local/self-hosted runner or ordinary cloud VM for functional tests, with a pinned Playwright/browser version, cached package installs, JSON/HTML reports, and failure traces. A sleeping laptop is an unreliable cron host. Keep backend-dependent multiplayer tests isolated and run against local Netlify Dev or an isolated test backend.
- Hardware rendering/performance: run separately on Patrick’s verified GPU machine, serially, at unchanged settings; keep the 75 FPS acceptance pending until qualifying hardware results exist.
- Use Netlify to host deploys and a small deployed smoke check. Run the large suite against localhost outside the Netlify build queue.
- For speed, use conservative workers per machine and shard across independent runners after establishing a stable baseline. Do not increase workers until timing-dependent failures and memory contention are understood.
- Add consistent test tags/projects for functional, GPU, benchmark, backend/multiplayer, narration, and manual iOS; add an explicit hardware prerequisite and suite-level timeout; persist per-commit results so the current status is inspectable. These are recommendations only.

Playwright itself recommends one worker on constrained CI and sharding for wider parallelization: [CI](https://playwright.dev/docs/ci), [sharding](https://playwright.dev/docs/test-sharding). Codex environments can prepare tools/dependencies and run project commands: [official environment documentation](https://learn.chatgpt.com/docs/environments/cloud-environments).
